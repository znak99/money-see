# Git 운영 전략

## 목적

money-see는 1인 개발과 AI Agent를 활용한 개발로 진행합니다. Git은 간단한 구조로 운영하며, 작업 이력을 통해 1~2주 후에도 무엇을 변경했는지와 어디서 이어서 작업해야 하는지 파악할 수 있도록 합니다.

## 저장소와 브랜치

- iOS와 Android를 하나의 저장소에서 관리합니다.
- 플랫폼별 소스와 빌드 설정은 분리하고, 프로젝트 지침과 작업 관리는 함께 유지합니다. 실제 폴더 이름은 프로젝트 생성 단계에서 확정합니다.
- `develop`은 일반 개발 브랜치입니다. 개발 작업과 문서 변경은 이 브랜치에서 진행합니다.
- `main`은 릴리즈 브랜치입니다. 일반 개발을 직접 진행하지 않습니다.
- 작업별 브랜치와 PR은 기본적으로 사용하지 않습니다.

## 커밋과 push

- 사용자가 지시한 작업이 완료되면 커밋합니다. 큰 작업은 독립적으로 설명할 수 있는 단계가 완료될 때 나누어 커밋합니다.
- 커밋에는 해당 작업에 속한 변경만 포함합니다. 서로 관계없는 변경은 별도 커밋으로 나눕니다.
- 변경한 플랫폼의 빌드와 관련 테스트를 수행합니다. 두 플랫폼을 변경했다면 양쪽 모두 검증합니다.
- 필수 빌드 또는 테스트가 실패하거나 수행하지 못했다면 커밋하지 않고 원인을 보고합니다.
- 화면과 애니메이션의 사용자 확인 대기는 빌드·테스트 결과와 구분하여 기록합니다. 사용자 확인 대기만으로 개발 커밋을 보류하지는 않습니다.
- 문서만 변경한 경우에는 문서 내용을 검토하고, 빌드·테스트 대상이 없음을 메시지에 기록합니다.
- 검증을 통과한 작업 내용은 `develop`에 커밋하되, 이 시점에는 push하지 않습니다. TASK.md 변경은 작업 내용 커밋에 포함하지 않습니다.
- 작업 내용 커밋 후 TASK.md를 완료 상태로 갱신하고, TASK.md 변경을 별도 문서 커밋으로 기록한 뒤 두 커밋을 함께 자동으로 push합니다.
- 큰 작업을 단계별로 커밋하는 경우에도 TASK.md 갱신을 별도 커밋으로 기록한 뒤 함께 push합니다. 전체 작업이 완료되기 전에는 `[진행 중]` 상태를 유지합니다.
- 점검·조사처럼 TASK.md 외에 변경한 파일이 없는 작업은 작업 내용 커밋을 생략합니다. 결과를 보고한 뒤 TASK.md 완료 기록만 커밋하여 자동으로 push하며, 빈 커밋을 만들지 않습니다.
- 기존 커밋을 수정하는 대신 후속 커밋을 추가하여 수정 이력을 남깁니다.
- push에 실패하면 실패 원인과 원격에 반영되지 않은 상태를 보고합니다.

## 커밋 메시지

### 제목

```text
종류: [대상] 구체적인 변경 결과
```

종류와 대상 표기는 아래 기준을 따르고, 제목의 설명과 본문은 한국어로 작성합니다.

| 종류 | 사용 기준 |
| --- | --- |
| `Feature` | 사용자에게 제공하는 기능 추가 또는 기존 기능의 동작·화면 개선 |
| `Fix` | 의도한 동작과 다른 오류 수정 |
| `Refactor` | 사용자에게 보이는 동작을 유지하면서 내부 코드 구조 개선 |
| `Test` | 테스트 추가 또는 수정 |
| `Docs` | 문서 추가 또는 수정 |
| `Chore` | 빌드 설정, 의존성, 개발 환경 등 유지보수 |

| 대상 | 사용 기준 |
| --- | --- |
| `[iOS]` | iOS에 해당하는 변경 |
| `[Android]` | Android에 해당하는 변경 |
| `[공통]` | 두 플랫폼에 걸친 변경 또는 프로젝트 전체 문서·설정 변경 |

- 종류는 커밋의 주된 목적에 따라 선택합니다. 기능 구현과 관련 테스트를 함께 포함하면 `Feature`를 사용합니다.
- 제목에는 변경한 화면이나 기능과 변경 결과를 함께 적습니다. "버그 수정", "UI 개선", "문서 수정"처럼 내용이 드러나지 않는 제목은 사용하지 않습니다.

### 본문

모든 커밋에 다음 네 항목을 작성합니다.

```text
목적:
- 변경이 필요한 이유

변경:
- 실제 변경한 내용

검증:
- 수행한 검증과 결과
- 사용자 확인 대기 또는 확인하지 못한 항목

남은 사항:
- 후속 작업, 알려진 문제 또는 결정이 필요한 사항
```

- `목적`에는 사용자가 얻는 효과나 해결할 문제를 설명합니다.
- `변경`에는 실제로 포함된 변경만 기록합니다. 코드 구조는 후속 작업을 이해하는 데 필요한 경우 설명합니다.
- `검증`에는 수행한 빌드·테스트와 결과를 구체적으로 적습니다. "테스트 완료"만으로 작성하지 않습니다.
- 화면·애니메이션은 사용자가 확인하기 전까지 "사용자 확인 대기"로 기록합니다.
- 문서 변경은 "문서 내용 검토 완료. 문서 변경만 포함하여 빌드·테스트 대상 없음"과 같이 작성합니다.
- `남은 사항`에는 해당 변경과 연결되는 후속 작업만 기록하며, 없으면 "없음"으로 작성합니다.
- 관련 TASK의 고정 ID를 `변경` 항목에 기록합니다. 예: `관련 작업: TASK-001`. 여러 작업이면 해당 ID를 모두 기록합니다.
- 날짜와 커밋 해시는 Git에 기록되므로 메시지에 반복하지 않습니다.

### 예시

```text
Feature: [iOS] 월급 입력값 저장 및 앱 재실행 시 복원 기능 추가

목적:
- 앱을 다시 열 때 월급을 매번 입력해야 하는 불편 해소

변경:
- 관련 작업: TASK-002 (예시 ID)
- 입력한 월급을 기기에 저장
- 앱 재실행 시 저장한 값을 입력 화면에 표시
- 저장된 값이 없으면 빈 입력 화면 표시

검증:
- iOS 빌드 통과
- 월급 저장 및 복원 테스트 통과
- 입력 화면의 표시와 조작은 사용자 확인 대기

남은 사항:
- 저장한 월급을 급여 증가 화면의 계산에 연결
```

## 릴리즈

- 사용자가 명시적으로 릴리즈를 지시했을 때만 `develop`을 `main`에 반영하고 버전 태그를 생성합니다.
- 릴리즈 버전은 사용자가 지정하거나 AI가 제안한 뒤 사용자와 확정합니다.
- iOS와 Android의 버전과 태그는 플랫폼별로 관리합니다.
  - iOS: `ios/v1.0.0`
  - Android: `android/v1.0.0`
- `main`에는 릴리즈 시점의 저장소 전체 상태가 반영됩니다. 플랫폼별 태그는 해당 플랫폼의 릴리즈를 나타냅니다.
- 릴리즈 반영 후 `main`과 생성한 태그를 원격 저장소에 push합니다.
- `main` 반영은 앱 스토어 배포를 의미하지 않습니다. 실제 배포는 사용자가 지시한 범위에 따라 수행합니다.

## 별도 지시가 필요한 작업

강제 push, 원격 브랜치·태그 삭제, 작업 내용을 버리는 명령은 별도 지시 없이 실행하지 않습니다.

## TASK.md와의 관계

작업 내용 커밋 → TASK.md 갱신 → TASK.md 별도 커밋 → 함께 push 순서로 진행합니다. 작업 관리의 기재 방법과 운영 규칙은 `docs/TASK_MANAGEMENT_GUIDE.md`에서 정의합니다.
